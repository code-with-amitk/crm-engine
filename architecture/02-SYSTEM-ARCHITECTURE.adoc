== Overview

The CRM Backend employs a layered, service-oriented architecture designed for scalability, maintainability, and reliability. The system consists of multiple containerized services that work together to provide a complete CRM solution.

== Architectural Layers

=== Layer 1: Transport & Security
**Components**: Nginx Reverse Proxy

* SSL/TLS termination for HTTPS
* CORS policy enforcement
* Request routing to appropriate backend service
* Load balancing for horizontal scaling
* DDoS protection and rate limiting

=== Layer 2: API Gateway & HTTP Layer
**Components**: Go HTTP Server (Gorilla Mux)

* Request handling and routing
* HTTP method validation (GET, POST, DELETE, etc.)
* Response formatting and serialization
* Health check endpoints

=== Layer 3: Authentication & Authorization
**Components**: JWT Middleware, Auth Handler

* Bearer token extraction from headers
* JWT signature validation
* Token expiration checks
* Tenant subscription verification
* Permission-based access control

=== Layer 4: Rate Limiting & Throttling
**Components**: Rate Limit Middleware

* IP-based rate limiting (login endpoints)
* User-based rate limiting (authenticated endpoints)
* Fixed-window counter algorithm
* Graceful rejection with 429 status

=== Layer 5: Business Logic
**Components**: REST Endpoints, Services

* Lead management logic
* Requirement processing
* Follow-up scheduling
* Employee management
* Notification triggering

=== Layer 6: Data Access Layer
**Components**: DB Utils Package

* SQL query building
* Parameter binding and escaping
* Connection pool management
* Transaction handling
* Error mapping to business errors

=== Layer 7: Persistence
**Components**: PostgreSQL Database

* ACID-compliant transactions
* Multi-tenant data isolation
* Foreign key constraints
* Indexes for query optimization
* Automated backups

## Data Flow Architecture

=== Typical Request Flow

[source, text]
----
1. USER INITIATES REQUEST
   └─> Mobile app sends: POST /leads with JSON body

2. NETWORK LAYER
   └─> Nginx receives on :443 (HTTPS)
       └─> Validates SSL certificate
       └─> Terminates TLS connection
       └─> Forwards plain HTTP to app on :8080

3. ROUTING LAYER
   └─> Gorilla Mux matches route to handler
   
4. AUTHENTICATION LAYER
   └─> Extract "Authorization: Bearer {token}"
   └─> Validate JWT signature with secret
   └─> Check token expiration
   └─> Extract claims (employee_id, tenant_id)
   └─> Return 401 if invalid

5. AUTHORIZATION LAYER
   └─> Check user's tenant subscription status
   └─> Verify subscription is active
   └─> Return 403 if expired

6. RATE LIMITING LAYER
   └─> Check user's request count in last minute
   └─> Return 429 if exceeded limit
   └─> Increment counter in memory

7. BUSINESS LOGIC LAYER
   └─> Parse request body JSON
   └─> Validate required fields
   └─> Perform business rules
     └─> Check if lead/employee exists
     └─> if does not exist, create and set followup
     └─> Transform data

8. DATA ACCESS LAYER
   └─> Build SQL INSERT query
   └─> Bind parameters (prevent SQL injection)
   └─> Execute within transaction
   └─> Commit or rollback on error

9. DATABASE LAYER
   └─> PostgreSQL processes transaction
   └─> Writes to lead table
   └─> Updates indexes
   └─> Returns inserted row

10. RESPONSE LAYER
    └─> Convert database result to JSON
    └─> Set HTTP status 201 Created
    └─> Write JSON response

11. NETWORK LAYER
    └─> Nginx forwards response
    └─> Mobile app receives JSON
----

## Service Communication

=== Synchronous Communication

**App ↔ PostgreSQL**

* REST API makes database queries
* Connection pooling for efficiency
* Transactions for consistency
* Prepared statements for security

**Nginx ↔ App**

* HTTP load balancing
* Connection reuse
* Keep-alive support

=== Asynchronous Communication

**Notifier ↔ Expo Push Service**

* Asynchronous, non-blocking
* Retry logic for failed deliveries
* No direct coupling

**Parser ↔ App**

* HTTP API calls for data creation
* Decoupled from main request flow
* Failures don't block main system

## Scalability Considerations

=== Horizontal Scaling (we prefer this)

The architecture supports adding more instances:

1. **API Servers**: Add more app containers behind load balancer
2. **Notifier Instances**: Multiple notifiers can safely coexist (use database locking for task distribution)
3. **Database Replication**: Read replicas for analytics queries
4. **Caching Layer**: Add Redis for session/token caching (future)

=== Vertical Scaling

Increase resources for single instance:
* More CPU for concurrent request handling
* More RAM for connection pooling
* Faster disk for database performance

=== Database Scaling

* Connection pooling to limit resource usage
* Indexing on frequently queried columns
* Query optimization for complex operations
* Partitioning for large tables (future)

## Reliability Features

=== High Availability

1. **Health Checks**: `/health` endpoint is provided for continous health checks.
2. **Graceful Shutdown**: Drains connections on SIGTERM
3. **Retry Logic**: Automatic retries for transient failures
4. **Circuit Breaker**: Prevent cascading failures

=== Data Durability

1. **ACID Transactions**: All writes are atomic
2. **Database Backups**: Regular snapshots
3. **Replication**: Data copied to standby nodes
4. **Write Ahead Logs**: Data persisted before acknowledged

=== Observability

1. **Structured Logging**: JSON logs for analysis
2. **Request Tracing**: Unique IDs for tracking
3. **Error Tracking**: Detailed error context
4. **Performance Metrics**: Response time, throughput

== Architecture Patterns Used

=== Layered Architecture
Separation of concerns with distinct layers (routing, auth, logic, persistence)

=== API Gateway Pattern
Nginx acts as single entry point for all client requests

=== Database Per Tenant
While data is in same database, queries are filtered by tenant_id (logical isolation)

=== Circuit Breaker
Rate limiting acts as circuit breaker for overloaded system

=== Health Check Pattern
Built-in health checks for load balancer integration
